# Continue ルール＋プロンプト集


## 配置と使い方

ワークスペース直下の `.continue/` に置くと、ルールは自動で適用され、プロンプトはチャット欄の `/` から呼べる。リポジトリに含めればチームで同じ設定を共有できる。

```
<ワークスペース>/
└─ .continue/
   ├─ rules/
   │  ├─ 00-common.md
   │  ├─ 10-csharp.md
   │  ├─ 20-tests.md
   │  └─ 30-review.md
   └─ prompts/
      ├─ plan.md
      ├─ implement.md
      ├─ gen-tests.md
      ├─ fix-error.md
      ├─ review.md
      ├─ summarize-spec.md
      └─ explain.md
```

- フロントマターの書式はContinueのバージョンで変わることがある。現場のバージョンで読み込まれるか、まず1ファイルで確認する
- ルールはモデルへの指示なので、短く断定で書く。小さいモデルほど長いルールを読み落とす
- 本番ツールが別製品になっても本文はそのまま流用できるよう、ツール固有の書き方はフロントマターだけに閉じ込める
- フレームワーク（xUnit / MSTest 等）や命名規約は、案件の標準が分かり次第書き換える

## ルールファイル

共通ルールは常に適用し、C#とテストは対象ファイルを開いたときだけ効かせる。

### 00-common.md

```markdown
---
name: 共通ルール
alwaysApply: true
---
- 回答は日本語。結論を先に書く。
- コードを変更する前に、変更するファイルと手順を3〜5行で示す。
- 変更は依頼された範囲の最小差分にする。無関係な整形やリネームをしない。
- 仕様が不明なときは推測で埋めず、「不明点」として質問を列挙する。
- 存在しないAPI、クラス、ファイルを作り上げない。確認できないときはそう書く。
- 変更後は確認方法（実行するビルド・テストのコマンド）を添える。
- 設計書の要件IDが与えられたら、対応箇所のコメントと回答にそのIDを記す。
```

### 10-csharp.md

```markdown
---
name: C#コーディング規約
globs: "**/*.cs"
---
- 命名: 型・メソッド・プロパティは PascalCase、ローカルと引数は camelCase、private フィールドは _camelCase。
- nullable 参照型を有効にした前提で書き、null の可能性を型で示す。
- 非同期メソッドは Async 接尾辞を付け、async void はイベントハンドラ以外で使わない。
- 例外を握りつぶさない。catch するならログを残して再スローか、対処理由をコメントする。
- マジックナンバーは名前付き定数にする。
- public メンバーには XML ドキュメントコメント（summary）を付ける。
- 1メソッドは約50行以内を目安にし、超えるときは分割を提案する。
```

### 20-tests.md

```markdown
---
name: テスト規約
globs: "**/*Tests/**/*.cs"
---
- フレームワークはプロジェクトで採用済みのものに合わせる。
- テスト名は メソッド名_条件_期待結果 の形にする。
- Arrange / Act / Assert を空行で区切り、1テストに検証観点は1つ。
- 正常系だけでなく、境界値・null・空・異常系を必ず含める。
- ファイル、時刻、通信などの外部依存はインターフェース経由で差し替える。
- テストを通すために本体コードや期待値を勝手に変えない。変える必要があれば理由を書いて確認を求める。
```

### 30-review.md

```markdown
---
name: レビュー観点
description: コードレビューを依頼されたときに適用する
alwaysApply: false
---
- 指摘は「重大（不具合・仕様違反）」「要改善」「提案」の3段階で分類する。
- 各指摘には対象箇所、理由、修正案を付ける。
- 確認する観点: 要件との一致、例外処理、null、境界値、スレッド安全性、リソース解放、テストの有無。
- 問題がなければ「重大な指摘なし」と明記し、無理に指摘を作らない。
```

## プロンプト集

7本で、計画から修正までの1周と、設計書要約・ジュニア向け解説をカバーする。`invokable: true` で `/plan` のように呼べる。

### plan.md — 実装計画

```markdown
---
name: plan
description: 要件から実装計画を作る
invokable: true
---
次の要件を実装する計画を作ってください。コードはまだ書かないでください。
出力:
1. 変更・追加するファイルとその理由
2. 実装ステップ（1ステップ=ビルドとテストで確認できる大きさ）
3. 各ステップのテスト観点
4. 不明点・確認したいこと
要件:
```

### implement.md — 1ステップずつ実装

```markdown
---
name: implement
description: 計画の指定ステップだけを実装する
invokable: true
---
先の計画のうち、指定したステップだけを実装してください。
- 他のステップには手を付けない
- 差分が分かる形で提示する
- 最後に確認用のビルド・テストコマンドを書く
対象ステップ:
```

### gen-tests.md — テスト生成

```markdown
---
name: gen-tests
description: 選択したコードの単体テストを書く
invokable: true
---
選択したコードの単体テストを書いてください。
先にテスト観点の一覧（正常系、境界値、異常系）を示し、その後にコードを書いてください。
仕様から期待値が決められないものは、テストを書かず「要確認」として挙げてください。
```

### fix-error.md — ビルド・テストエラーの修正

```markdown
---
name: fix-error
description: エラー出力から原因と最小修正を示す
invokable: true
---
以下はビルドまたはテストの出力です。
1. 原因を1〜3行で説明
2. 最小の修正案を提示
3. テスト側を変えるべき場合は理由を書き、確認を求める
同じエラーへの修正が3回目なら修正をやめ、考えられる原因を列挙して人に判断を仰いでください。
出力:
```

### review.md — レビュー

```markdown
---
name: review
description: 選択したコードをレビューする
invokable: true
---
選択したコードを「レビュー観点」ルールに従ってレビューしてください。
対応する要件があれば以下に貼ります。要件との食い違いを最優先で指摘してください。
要件:
```

### summarize-spec.md — 設計書の要約

```markdown
---
name: summarize-spec
description: 設計書の節をID付き要件リストにする
invokable: true
---
以下の設計書の節を、実装で使える要件リストにしてください。
- 1行1要件、「【節番号-連番】要件」の形
- 入力・出力・制約・異常時の振る舞いを区別する
- 曖昧な記述、他節への参照は「要確認」として別に列挙する
- 書かれていないことを補わない
設計書:
```

### explain.md — ジュニア向け解説

```markdown
---
name: explain
description: 選択したコードを初学者向けに解説する
invokable: true
---
選択したコードを、C#を学び始めた人向けに解説してください。
1. 何をするコードか（1〜2行）
2. 処理の流れ
3. 初学者がつまずきやすい文法・考え方
4. 理解を確かめる問題を2問（答えは最後に）
```

## 手動で回す修正ループ

自律ツールが無い間は、同じループを人がプロンプトを呼んで回す。本番ツールが来たら、この流れと停止条件をそのまま自動化の仕様にする。

&#91;embedded content: 手動で回す修正ループ · 人の判断は2箇所\]

エラー出力はそのまま /fix-error に貼る。修正回数、採用した提案数、所要時間を記録しておくと、WBS 5.4 の比較計測にそのまま使える。
